# WorldBackUp

[![build](https://github.com/bouz3337-cell/WorldBackUp/actions/workflows/build.yml/badge.svg)](https://github.com/bouz3337-cell/WorldBackUp/actions/workflows/build.yml)

마인크래프트 **26.2** 서버용 자동 백업 / 롤백 플러그인.
월드·플레이어 데이터를 일정 주기로 압축 보관하고, 테러(그리핑)를 당하면 원하는 시점으로 서버를 통째로 되돌립니다.

- 외부 라이브러리 의존성 0개 (JDK 기본 zip + Bukkit YAML만 사용)
- 압축은 비동기 스레드에서 처리 → 서버 렉 최소화
- **차등 백업** 지원 → 큰 월드에서 백업 용량·시간을 수십 분의 1로 (`backup.mode`)
- 압축이 끝나야 최종 파일명이 붙으므로 **반쯤 만들어진 백업이 정상으로 오인되지 않음**
- 복원 전에 zip 무결성을 검사해서 **깨진 백업으로 월드만 날리는 사고를 차단**
- 복원은 "예약 → 서버 종료 → 다음 부팅 시 월드 로드 전 교체" 방식이라 파일 잠금 문제 없음

---

## 1. 요구 사항

| 항목 | 값 |
|---|---|
| 서버 | Paper 26.2 (Spigot 계열 호환) |
| Java | **25 이상** (26.1부터 마인크래프트가 Java 25를 요구) |
| 빌드 | Gradle Wrapper 포함 (별도 설치 불필요) |

## 2. 빌드

```bash
./gradlew build
# 결과물: build/libs/WorldBackUp-1.3.1.jar

# 서버 plugins 폴더로 바로 복사하려면
./gradlew deployPlugin -PserverDir="D:/minecraft/server"
```

`build/libs/WorldBackUp-1.3.1.jar` 를 서버의 `plugins/` 폴더에 넣고 재시작하면
`plugins/WorldBackUp/config.yml` 이 생성됩니다.

빌드하지 않고 쓰시려면 [Releases](https://github.com/bouz3337-cell/WorldBackUp/releases) 에서
jar 를 내려받으세요. 버전을 올릴 때 무엇이 바뀌는지는 [CHANGELOG.md](CHANGELOG.md) 에 있습니다.

### 업데이트하기

> **jar 교체는 월드 파일을 건드리지 않습니다.** 아래에서 "알아서 정리한다" 는 것은
> `config.yml` 과 백업 이야기입니다. 월드는 백업할 때 **읽기만** 하고, 쓰는 것은
> `/wb restore` 뿐입니다.

**`/wb update` 를 치면 알아서 받아 둡니다.** 다음에 서버를 켜면 적용됩니다.

```
/wb update
→ 새 버전 1.3.0 을 받았습니다.
  서버를 다시 켜면 자동으로 갈아 끼워집니다. 지금 돌고 있는 1.2.0 은 그대로 둡니다.
```

받은 jar 는 `plugins/update/` 에 놓입니다. 서버가 다음에 켜질 때 스스로 `plugins/` 로 옮기고
옛 jar 를 치웁니다 — 돌고 있는 jar 를 그 자리에서 바꾸지 않으므로 잠긴 파일 문제도,
옛 jar 가 함께 남는 문제도 없습니다.

시작할 때도 새 버전이 있는지 한 번 확인해 콘솔에 알립니다(`update.check`, 기본 켜짐).
확인만 하고 내려받지는 않습니다.

**`update.auto-download: true`** 로 두면 그 확인에서 자동으로 받아 둡니다. 앞으로는
`/wb update` 를 치지 않아도 켤 때마다 최신으로 따라갑니다.

> ⚠️ 켜기 전에 한 번 생각해 보세요. 이 값이 `true` 면 서버는 앞으로 그 저장소에 올라오는
> 코드를 **사람 확인 없이 받아서 실행합니다.** 저장소 계정이 털리면 그대로 따라갑니다.
> 기본값이 `false` 인 이유이고, 필요할 때 `/wb update` 로 직접 받는 편이 안전합니다.
>
> 받은 파일은 그대로 믿지 않습니다 — `https` 인지, 깃허브 주소인지, 정말 zip 인지,
> 안의 `plugin.yml` 이 WorldBackUp 이고 버전이 맞는지 확인한 뒤에야 자리에 놓습니다.
> 하나라도 어긋나면 지우고 아무 일도 없던 것으로 둡니다.

### 손으로 바꾸기

**jar 만 바꾸면 됩니다.** 설정 파일도, 백업도 손대지 않아도 됩니다.

```
1) 서버를 끕니다
2) plugins/ 의 옛 WorldBackUp jar 를 지우고 새 jar 를 넣습니다
3) 서버를 켭니다
```

2번에서 **옛 jar 를 반드시 지우세요.** 파일 이름에 버전이 들어 있어서 넣기만 하면 두 개가
공존하는데, 그러면 어느 쪽이 올라올지는 서버가 폴더를 읽는 순서에 달립니다. 그렇게 되면
시작할 때 콘솔이 크게 알려 줍니다.

시작하면 플러그인이 알아서 정리합니다.

- 새로 생긴 설정을 **설명(주석)까지 그대로** `config.yml` 에 끼워 넣습니다.
  관리자가 쓴 줄은 값도 주석도 순서도 한 줄도 건드리지 않습니다.
- **백업을 지울 수 있는 설정은 "지금 그대로" 인 값으로 들어옵니다.** jar 를 바꾸는 것만으로
  되돌릴 시점이 줄지 않게 하기 위해서입니다. 무엇이 그렇게 들어왔는지는 콘솔에 뜨고,
  켜는 방법은 `config.yml` 그 자리에 주석으로 들어갑니다 — 주석만 풀고 `/wb reload` 하면 됩니다.

  > 막는 것은 **지우는** 변화뿐입니다. 백업을 <b>키우는</b> 변화(`targets.plugins: all` 처럼)는
  > 기본값 그대로 들어옵니다 — 백업이 커진 것은 나중에 줄일 수 있지만, 백업에 없는 경제 잔고는
  > 되돌릴 수 없습니다. 두 실패의 대가가 비대칭입니다.
- 옛 백업은 그대로 쓸 수 있습니다. 1.0.0 이 만든 전체·차등 백업 모두 복원되고,
  `/wb lock` 으로 잠근 백업도 정리에서 빠집니다.

> 새 기본값은 **새로 설치하는 서버**의 것입니다. 이미 돌던 서버는 관리자가 읽고 켜기 전까지
> 하던 대로 돕니다. 백업 플러그인에서 "업데이트했더니 되돌릴 시점이 줄어 있더라" 는 것은
> 가장 나쁜 실패라, 새 기능보다 지금 동작을 지키는 쪽을 택했습니다.
> 이 약속은 [`UpgradeFromOneZeroSimulationTest`](src/test/java/io/github/yj/worldbackup/UpgradeFromOneZeroSimulationTest.java)
> 가 1.0.0 서버를 통째로 재현해 지킵니다.

**업그레이드는 jar 만 갈아 끼우면 됩니다.** 새 버전에서 생긴 설정은 시작할 때
`config.yml` 에 **설명 주석째** 채워 넣고 콘솔에 이름을 남깁니다. 여러분이 바꾼 값과
직접 단 주석은 한 줄도 건드리지 않습니다.

## 3. 명령어

기본 명령어는 `/worldbackup`, 별칭은 `/wb`, `/wbackup` 입니다.

| 명령어 | 설명 | 권한 |
|---|---|---|
| `/wb backup [메모]` | 지금 즉시 백업 | `worldbackup.backup` |
| `/wb oneback` | **서버 한 벌을 통째로.** 이 폴더만 챙기면 아무 데서나 다시 열 수 있음 | `worldbackup.backup` |
| `/wb list [페이지\|날짜]` | 백업 목록 (클릭하면 상세 정보) | `worldbackup.use` |
| `/wb list days` | **날짜별 보유 현황.** 몇 주 전 것을 찾을 때 | `worldbackup.use` |
| `/wb info [ID\|번호]` | 백업 상세 정보 | `worldbackup.use` |
| `/wb restore` | **되돌릴 시점 목록.** 클릭해서 고름 | `worldbackup.restore` |
| `/wb restore [ID\|번호] (worlds)` | 해당 시점으로 롤백 요청 | `worldbackup.restore` |
| `/wb restore at [시각]` | 그 시각 이전 백업으로 롤백 요청 | `worldbackup.restore` |
| `/wb confirm` | 롤백 확정 (안전 백업 → 카운트다운 → 종료) | `worldbackup.restore` |
| `/wb cancel` | 롤백 요청/카운트다운 취소 | `worldbackup.restore` |
| `/wb delete [ID\|번호] (cascade)` | 백업 삭제 (`cascade` 는 딸린 차등본까지) | `worldbackup.delete` |
| `/wb lock` / `/wb unlock` | 자동 삭제 보호 설정/해제 | `worldbackup.delete` |
| `/wb prune` | 보관 정책을 지금 즉시 적용 | `worldbackup.delete` |
| `/wb status` | 다음 백업 시각, 용량, 디스크 여유 | `worldbackup.use` |
| `/wb reload` | config.yml 다시 불러오기 | `worldbackup.reload` |
| `/wb update` | 새 버전 확인 후 받아 두기 (다음 재시작에 적용) | `worldbackup.reload` |

### ID 자리에 쓸 수 있는 것

사고를 발견했을 때 아는 것은 백업 ID 가 아니라 **시각**입니다. 그래서 시각으로도 찾을 수 있습니다.

| 입력 | 뜻 |
|---|---|
| `latest` | 가장 최근 백업 |
| `#3` 또는 `3` | `/wb list` 의 번호 |
| `20260816-030000` | 백업 ID |
| **`9h`** `30m` `2d` | 그만큼 전 **이전**의 가장 최근 백업 |

콜론이 든 시각은 `at` 을 붙여 주세요. 마인크래프트 명령어 인자는 콜론과 공백을 받지 못합니다.

| 입력 | 뜻 |
|---|---|
| `/wb restore at 03:00` | 가장 가까운 과거의 그 시각 **이전** 백업 |
| `/wb restore at 2026-08-16 03:00` | 절대 시각 **이전** 백업 |
| `/wb restore at 9h` | `at` 뒤에는 위 형식도 다 됩니다 |

모두 **"그 시점 이전"** 을 고릅니다. 사고 시각을 말했는데 그 이후 백업이 잡히면 피해가 담긴 상태로
되돌리게 되므로, 요청을 넘기느니 조금 더 과거로 갑니다. 무엇을 골랐는지는 실행 시 알려 줍니다.

```
/wb restore 9h
→ 요청 2026-08-16 03:00:00 → 그 이전 가장 최근 백업 2026-08-16 02:45:00 (15분 더 과거)
```

목록 번호(`#3`)는 백업이 하나 생기거나 정리될 때마다 밀립니다. 급할 때는 시각 쪽이 안전합니다.

### 탭 완성

`Tab` 을 누르면 **시각 표현이 위, 백업 ID 가 아래**로 묶여 나오고, 각 줄에는 그것이 실제로
가리키는 백업이 적혀 있습니다. 눌렀을 때 어디로 되돌아가는지 모르는 채 고르지 않도록 한 것입니다.

```
/wb restore <Tab>
  latest            가장 최근 → 2026-08-17 09:15:00 · 48.2 MB · 자동 · 차등
  1h                1시간 전 → 2026-08-17 08:15:00 · 45.8 MB · 자동 · 차등
  12h               12시간 전 → 2026-08-16 21:00:00 · 2.1 GB · 자동
  1d                1일 전 → 2026-08-16 09:00:00 · 2.0 GB · 자동
  20260817-091500   2026-08-17 09:15:00 · 48.2 MB · 자동 · 차등
  …
```

- 보관 범위 밖이라 고를 수 없는 시각(`7d` 인데 7일 전 백업이 없는 경우)은 **아예 뜨지 않습니다.**
- 여러 시각이 같은 백업 하나로 모이면 **한 줄로만** 보여 줍니다. 고를 것이 많은 것처럼 보이지 않도록.
- 백업 ID 는 아무것도 입력하지 않았을 때 최근 5개만 뜹니다. 똑같이 생긴 숫자 덩어리가 화면을 덮으면
  정작 필요한 시각 표현이 묻히기 때문입니다. ID 를 직접 치기 시작하면 그때부터 넓게 찾습니다.
- 인벤토리가 없거나(`플레이어 없음`) 복원할 수 없는(`손상`) 백업은 그 자리에서 표시됩니다.

`/wb list <Tab>` 도 같은 방식입니다. 날짜마다 그 날 몇 개가 어느 시간대에 있는지 함께 뜹니다.

`/wb restore [ID] worlds` 는 월드 폴더만 되돌리고 `server.properties` 등 서버 설정 파일은 유지합니다.
백업에 월드 정보가 없어 대상을 못 고르면 전체를 덮어쓰지 않고 **거부합니다.**

`cascade` 는 딸린 차등본까지 지우지만, 그 중 `/wb lock` 으로 잠근 것이 하나라도 있으면
전체를 거부합니다. 기준을 지우는 것은 곧 그 차등본을 못 쓰게 만드는 것이기 때문입니다.

권한 `worldbackup.admin` 은 위 모든 권한을 포함하며, 기본값은 모두 OP 입니다.

## 4. 테러 당했을 때 (롤백 절차)

```
1) /wb restore     -> 되돌릴 시점 목록이 뜹니다. 원하는 걸 클릭
2) 경고문과 대상 확인
3) /wb confirm     -> 현재 상태를 안전 백업 후 카운트다운 시작
4) 서버가 자동 종료됨
5) 서버를 다시 켬  -> 월드가 로드되기 전에 복원이 적용됨
```

`/wb restore` 는 백업 ID 를 몰라도 되도록 시점을 골라 줍니다.

```
───── 되돌릴 시점 고르기 ─────
보관 범위: 16일 0시간 전까지 (2026-08-01 09:00:00)
 [가장 최근]  2026-08-17 09:15:00 · 48.2 MB (12분 전) [차등]
 [30분 전]    2026-08-17 08:45:00 · 46.1 MB (42분 전) [차등]
 [1시간 전]   2026-08-17 08:15:00 · 45.8 MB (1시간 12분 전) [차등]
 [3시간 전]   2026-08-17 06:00:00 · 44.0 MB (3시간 27분 전) [차등]
 [12시간 전]  2026-08-16 21:00:00 · 2.1 GB (12시간 27분 전)
 [1일 전]     2026-08-16 09:00:00 · 2.0 GB (1일 0시간 전)
 [3일 전]     2026-08-14 12:00:00 · 1.9 GB (2일 21시간 전)
─────────────────────────────
클릭하면 확인 화면이 뜹니다. 실제 복원은 /wb confirm 을 눌러야 시작됩니다.
```

각 줄은 그 시점에 **실제로 있는 백업**을 가리킵니다. 눌렀을 때 어디로 돌아가는지가
줄에 그대로 적혀 있고, 인벤토리가 없는 백업이면 `[플레이어없음]` 이 붙습니다.
보관이 성긴 구간에서 여러 시점이 같은 백업으로 모이면 한 줄로만 보여 줍니다 —
선택지가 많은 것처럼 착각하지 않도록.

- 3번 단계에서 만들어지는 `복원 직전` 백업 덕분에, 잘못 되돌렸다면 그 백업으로 다시 되돌릴 수 있습니다.
- 교체된 기존 파일은 삭제되지 않고 `plugins/WorldBackUp/replaced/<시각>/` 에 보관됩니다
  (`restore.keep-replaced-files: false` 로 끄면 바로 삭제).
  월드 전체 크기만큼 쌓이므로 `restore.keep-replaced-max` 개(기본 3개)만 남기고 자동 정리됩니다.
- 복원 결과는 콘솔과 `plugins/WorldBackUp/last-restore.yml` 에 기록됩니다.
- **밴은 되돌아가지 않습니다.** 테러범을 밴하고 되돌려도 그 밴은 그대로 유지됩니다.
- op·화이트리스트는 그 시점으로 돌아갑니다. **누가 op 가 되고 누가 내려갔는지는 콘솔에
  이름으로 남으니 5번 단계 직후 한 번 확인하세요.** 되돌린 백업이 op 가 없던 시점이라면 게임 안에서
  올릴 수 없으므로, 콘솔에서 `op <이름>` 을 쓰면 됩니다.
- `server.properties` 처럼 이번 세션에 적용할 수 없는 파일이 있으면 콘솔이 이름을 알려 줍니다.
  거기까지 맞추려면 서버를 한 번 더 껐다 켜세요.

> **자동 재시작 필수** — 플러그인은 서버 프로세스를 다시 켤 수 없습니다.
> 호스팅 패널의 자동 재시작을 켜두거나, 아래 [무인 운영](#5-무인-자동-운영) 절의 래퍼를 쓰세요.

## 5. 무인 자동 운영

관리자가 콘솔을 보지 않는 환경을 위해 두 가지 안전장치가 들어 있습니다.

**① 백업이 전멸하지 않습니다 (`retention.min-backups`)**

접속자가 없으면 백업은 건너뛰지만 보관 정리는 계속 돕니다. 그래서 서버가 `max-age-days`
보다 오래 놀면 백업이 **하나도 남지 않을 수** 있었습니다 (`keep-daily` 는 "최근 N일 안에
만들어진 백업"만 지키는데 그 기간에 백업이 없고, 자동 백업은 `protect-manual` 대상도 아님).
그 상태에서 누가 접속해 테러를 하면 되돌릴 곳이 없습니다.
`min-backups` 는 어떤 정책으로도 그 아래로 내려가지 않는 하한선입니다.

**② 복원이 실패하면 자동 작업이 멈춥니다**

복원이 중간에 실패하면 `plugins/WorldBackUp/restore-failed-<시각>.yml` 이 생기고,
이 파일이 있는 동안 **자동 백업과 보관 정리(`replaced/` 정리 포함)를 하지 않습니다.**
그러지 않으면 반쯤 복원된 월드가 계속 백업되면서 멀쩡한 예전 백업이 정책에 밀려 사라집니다.

- 수동 `/wb backup`, `/wb restore` 는 그대로 쓸 수 있습니다.
  다만 그 백업 **뒤에 따라붙는 보관 정리는 건너뜁니다** — 상황을 보려고 한 번 백업한 것이
  멀쩡한 예전 백업을 밀어내면 정지를 걸어 둔 의미가 없습니다.
  디스크가 모자라도 옛 백업을 지워 공간을 만들지 않고 그 백업만 실패합니다
- `/wb status` 맨 위에 정지 상태가 표시됩니다
- 월드를 확인한 뒤 그 파일을 지우고 `/wb reload` 하면 풀립니다
- 이후 복원이 성공하면 표식에 `.resolved` 가 붙으며 자동으로 풀립니다

**③ 서버 재시작 래퍼**

`/wb confirm` 이후 서버는 스스로 꺼지므로, 누군가 다시 켜야 복원이 적용됩니다.
바로 쓸 수 있는 것을 [`extras/`](extras/) 에 넣어 두었습니다.

| 파일 | 쓰는 법 |
|---|---|
| [`extras/run-server.ps1`](extras/run-server.ps1) | 서버 폴더에 두고 실행. 끌 때는 `STOP` 빈 파일을 만든 뒤 `/stop` |
| [`extras/minecraft.service`](extras/minecraft.service) | `/etc/systemd/system/` 에 복사 후 `systemctl enable --now minecraft` |

둘 다 자기 파일 맨 위에 java 인자(메모리·jar 이름)가 있으니 서버에 맞게 고치세요.
PowerShell 쪽은 **복원이 실패하면 자동 재시작을 멈춥니다** — 사람이 월드를 확인해야 하는
상황에서 그대로 다시 켜면 반쯤 복원된 월드로 서버가 계속 돌아가기 때문입니다.
크래시 루프(1분 내 3회 사망)도 멈춥니다.

**무인 운영 권장 설정**

```yaml
backup:
  on-startup: true              # 재시작 후 상태를 한 번 남김
  skip-if-no-players: true
  directory: "D:/minecraft-backups"   # 절대 경로, 다른 물리 디스크
retention:
  min-backups: 5                # 0 으로 두지 마세요
restore:
  verify-archive: true
  create-safety-backup: true
```

> 백업본을 다른 물리 디스크·다른 장비로 복사하는 것은 이 플러그인이 하지 않습니다.
> 디스크 하나가 죽으면 월드와 백업이 함께 사라지므로, 백업 폴더를 외부로 옮기는 절차는
> 별도로 두세요.

### 백업 폴더를 plugins 밖에 두기

기본값은 `plugins/WorldBackUp/backups/` 입니다. 그 자리는 **플러그인을 지우거나 다시 설치할 때
함께 날아가기 쉽고**, `plugins/` 를 통째로 다루는 호스팅 패널·동기화 스크립트에도 걸립니다.
옮기고 싶다면 `backup.directory` 하나만 바꾸면 됩니다.

| 값 | 실제 위치 |
|---|---|
| `"backups"` (기본값) | `plugins/WorldBackUp/backups/` |
| `"../../worldbackups"` | **`서버폴더/worldbackups/`** (plugins 밖) |
| `"D:/minecraft-backups"` | 그 경로 그대로 (**다른 디스크 — 가장 권장**) |

상대 경로는 **`plugins/WorldBackUp/` 기준**이라 서버 폴더로 가려면 두 단계 올라갑니다.
헷갈리면 절대 경로를 쓰세요. 어디에 두든:

- 그 폴더는 **백업 대상에서 자동으로 빠집니다.** 서버 폴더 안에 두어도 백업이 자기 자신을
  삼키지 않습니다. (기본 위치에 남아 있는 옛 아카이브도 계속 제외됩니다)
- `/wb status` 의 `저장 위치` 에 실제 절대 경로가 표시되니 바꾼 뒤 확인하세요.
- 디스크 여유·총 용량 상한은 그 폴더가 있는 파일시스템 기준으로 잽니다.

> **이미 만들어진 백업은 따라오지 않습니다.** 값만 바꾸면 플러그인은 새 폴더를 보므로
> `/wb list` 가 비어 보입니다. 옮기려면 서버를 끄고 `wb-*.zip` 과 짝이 되는 `wb-*.yml`,
> `wb-*.locked` 를 **함께** 새 폴더로 옮긴 뒤 켜서 `/wb list` 로 확인하세요.
> (`.yml` 을 빠뜨려도 zip 안에 사본이 있어 복구되지만, `.locked` 를 빠뜨리면 보호가 풀립니다)

### 차등 백업 (용량·시간 절감)

**기본값은 `differential` 입니다.** 아래 `retention.tiers` 기본값이 27개를 남기는데,
`full` 이면 그 27개가 전부 "월드 한 벌씩" 이라 디스크가 먼저 차기 때문입니다.

```yaml
backup:
  mode: differential
  full-every: 24    # 30분 주기 기준 하루 한 번 전체 백업
```

`full` 은 백업 하나하나가 독립적이라 가장 단순합니다. 그쪽을 쓰시려면 `tiers` 의 `keep`
값을 크게 줄이거나 `tiers` 를 비우세요. 두 값이 어긋나면 서버 시작 시 콘솔에 경고가 뜹니다.

> **이미 쓰고 계신 서버라면 — 저절로 바뀌지 않습니다.**
> 업그레이드는 빠진 설정을 끼워 넣을 뿐 **이미 있는 값은 바꾸지 않습니다.** 예전 버전에서
> 받은 `mode: full` 이 그대로 남고 동작도 그대로입니다. 바뀌는 것은 딱 하나 —
> `full` 과 깊은 `tiers` 를 함께 쓰고 계셨다면 이제 시작할 때 콘솔에 경고가 뜹니다.
> 그 경고를 보셨다면 둘 중 하나를 고르시면 됩니다.
>
> - **`mode: differential` 로 바꾸기** — 계단을 그대로 두고 용량만 줄입니다. 갖고 계신
>   **가장 최근 전체 백업이 그대로 기준이 되므로** 월드를 다시 통째로 압축하지 않고, 바로
>   다음 백업부터 차등본이 쌓입니다. 예전 `full` 백업들은 하나하나가 독립적이라 그대로
>   복원에 쓸 수 있습니다.
> - **`tiers` 의 `keep` 줄이기 (또는 `tiers` 비우기)** — `full` 의 단순함을 지키는 대신
>   되돌릴 수 있는 시점의 수를 포기합니다.
>
> 어느 쪽이든 고친 뒤 `/wb reload` 면 반영됩니다.

전체 백업 하나를 기준으로, 이후에는 **크기와 수정 시각이 달라진 파일만** 저장합니다.
10GB 월드라면 차등본 하나가 보통 수십~수백 MB입니다.

동작 방식:

- 각 백업 zip 에는 그 시점의 **전체 파일 목록**(`worldbackup-files.txt`)이 들어갑니다.
  복원할 때 이 목록이 정답이 되어, 차등본에 없는 파일은 기준 백업에서 꺼내 오고
  그 사이 삭제된 파일은 되살리지 않습니다.
- 기준 백업은 딸린 차등본이 모두 정리되기 전까지 **자동 삭제되지 않습니다.**
  `/wb delete` 로 직접 지우려 해도 막히고, 함께 지우려면 `/wb delete <ID> cascade` 를 씁니다.
  차등본을 압축하고 있는 동안에도 그 기준은 보관 정책·공간 확보·수동 삭제 어느 쪽으로도 지워지지 않습니다.
- 디스크 여유 검사는 **이번에 실제로 저장할 용량** 기준입니다. 차등본 하나가 200MB 라면
  월드 전체 크기가 아니라 그 200MB 로 판단하므로, 공간이 넉넉한데 백업이 거부되는 일이 없습니다.
- 기준 백업이 사라진 차등본은 `/wb list` 에 `[손상]` 으로 뜨고 복원에 쓸 수 없습니다.
- 복원 검증(`restore.verify-archive`)은 기준과 차등본 **양쪽**을 읽고, 파일 목록의 모든 항목이
  둘 중 어딘가에 실제로 있는지까지 확인합니다.
- 복원 직후 첫 백업은 기준을 새로 잡기 위해 자동으로 전체 백업이 됩니다.

> 변경 판단은 **크기 + 수정 시각** 기준입니다. 내용이 바뀌었는데 둘 다 동일한 파일은
> 감지하지 못합니다. 마인크래프트 region/playerdata 파일은 쓸 때마다 수정 시각이 바뀌므로
> 실사용에서는 문제되지 않지만, 완전한 독립성이 필요하면 `mode: full` 을 쓰세요.

### 몇 주 전 백업 찾기

목록을 여러 장 넘기는 대신 **날짜별 현황**에서 짚습니다.

```
/wb list days
 2026-08-17 (오늘)  24개  00:15~09:15 · 1.2 GB     ← 클릭하면 그 날 목록
 2026-08-16 (어제)  18개  00:45~23:45 · 900 MB
 2026-08-15          4개  06:00~18:00 · 210 MB
 2026-08-14          1개  23:30       ·  52 MB
 2026-08-11          1개  23:30       ·  52 MB
```

이 화면이 **계단식이 실제로 도는지 보여 주는 화면**이기도 합니다. 오늘은 촘촘하고
과거로 갈수록 개수가 줄어드는 모양이면 계단이 동작하는 것입니다. 날짜마다 개수가
똑같다면 계단이 꺼져 있는 것입니다.

```
/wb list 2026-08-01          그 날짜의 백업만
/wb restore at 2026-08-01 03:00   그 시각 이전으로 바로 되돌리기
/wb restore 21d                   21일 전 이전으로
```

`/wb list` 위쪽에는 **보관 범위**가 뜹니다. 없는 시점을 뒤지느라 시간 쓰지 않도록,
가장 오래된 백업이 언제인지 먼저 보여 줍니다.

### 계단식 보관 — 자는 동안 당한 테러를 견디려면

24시간 서버에서 가장 곤란한 상황은 **새벽에 테러당하고 아침에 발견**하는 것입니다.
기본 정책(30분 주기 / 48개 / `keep-daily`)은 **정확히 24시간**만 촘촘하게 덮고,
하루가 넘으면 "하루 1개"로 뚝 떨어집니다. 게다가 `keep-daily` 는 **그 날의 마지막** 백업을
남기므로, 새벽에 당했다면 살아남은 그 하나에 이미 피해가 들어 있습니다.

`retention.tiers` 는 최근일수록 촘촘히, 오래될수록 성기게 남깁니다.

**이것이 기본값입니다.** (새로 설치하는 경우)

```yaml
retention:
  tiers:
    - { every: 0,   keep: 8 }    # → 4시간    30분 해상도 (= 백업 주기 × keep)
    - { every: 1h,  keep: 10 }   # → 14시간   1시간 해상도  ← 자는 동안
    - { every: 6h,  keep: 2 }    # → 26시간
    - { every: 24h, keep: 3 }    # → 약 4일
    - { every: 72h, keep: 4 }    # → 약 16일
```

**자는 구간이 1시간 해상도**입니다. 새벽 3시 사고를 정오에 발견해도 2시대 백업으로 돌아가
잃는 것이 최대 1시간입니다. 기본값인 30분 주기 기준 총 27개로 약 16일이 덮입니다.

> `every: 0` 계단만은 시간이 아니라 개수로 셉니다. 그래서 그 계단이 덮는 시간은
> **`interval-minutes` × `keep`** 이고, 주기를 바꾸면 함께 움직입니다.
> (30분 × 8 = 4시간. 15분 주기로 줄이면 2시간이 되고 해상도가 두 배 촘촘해집니다)

> **`mode: differential` 전제입니다.** `full` 이면 27개가 전부 월드 한 벌씩이라 감당이 안 됩니다.
> 그래서 `backup.mode` 의 기본값도 `differential` 입니다. 굳이 `full` 로 두시면 서버 시작 시
> 콘솔에 경고가 뜨는데, 무시하면 디스크가 먼저 차서 **아래 계단은 만들어지지도 못합니다.**

### 용량은 깊이가 결정합니다

오래된 구간의 대표로는 **전체 백업**이 뽑힙니다(차등본을 남기면 그 기준까지 붙잡아야 해서
오히려 두 배가 듭니다). 그래서 총 용량은 이렇게 잡힙니다.

```
총 용량 ≈ (깊은 계단 슬롯 수) × (전체 백업 하나 크기)
```

기본값은 깊은 슬롯이 약 10개입니다. 월드가 압축 후 2GB면 **약 26GB**입니다.
깊이를 늘리면 정비례해 늘어나므로, `{ every: 72h, keep: N }` 의 `N` 이 사실상 용량 손잡이입니다.

**자는 동안 구간(최근 12시간)은 거의 공짜입니다** — 전부 차등본이라 다 합쳐도 2GB가 안 됩니다.
용량이 부담되면 깊이만 줄이세요. 사고 대응 능력은 그대로입니다.

### 총 용량 상한 — 호스팅이면 반드시

```yaml
retention:
  max-total-size-gb: 40    # 할당량 70GB 기준
```

`min-free-disk-gb` 는 파일시스템에 남은 공간을 묻는데, **컨테이너 호스팅에서는 그 값이
호스트 디스크를 가리켜 정작 걸려 있는 할당량을 보지 못합니다.** 그러면 백업이 할당량을
향해 자라도 아무도 막지 않습니다.

`max-total-size-gb` 는 백업 폴더 크기를 직접 재므로 그런 환경에서도 동작하고, 계단을
잘못 잡아 예상보다 많이 쌓이는 경우에도 마지막 방어선이 됩니다.
`/wb status` 에 사용률이 함께 표시됩니다.

> `/wb lock` 으로 잠근 백업과 `min-backups` 는 이 상한보다 **우선합니다.**
> 용량을 맞추려다 되돌릴 백업을 하나도 안 남기는 것이 더 나쁘기 때문입니다.
> 상한을 못 맞추면 조용히 넘어가지 않고 콘솔에 알립니다.

> **계단은 이어서 쌓입니다.** 각 계단은 앞 계단이 끝난 지점부터 과거로 갑니다.
> 위에서 `{ every: 1h, keep: 10 }` 은 "최근 4시간" 다음부터 10시간을 더 덮어 14시간까지를
> 담당합니다. 그래서 **`keep: 1` 짜리 계단은 그 구간 폭만큼을 통째로 잃습니다** —
> `{ every: 6h, keep: 1 }` 로 덮인 시간대는 되돌릴 때 최대 6시간치가 날아갑니다.
> 자주 쓸 시간대일수록 `keep` 을 키우세요. 실제 누적 범위는 `/wb status` 가 보여 줍니다.
>
> ```
> 보관 정책: 계단식 6단계 (최대 38개)
>    · 최신 8개          → 4시간 0분까지
>    · 1시간 0분마다 × 10개 → 14시간 0분까지
>    · 3시간 0분마다 × 4개  → 1일 2시간까지
> ```

- `tiers` 를 설정하면 `max-backups`·`max-age-days`·`keep-daily` 를 **대신합니다.**
  둘을 섞으면 계단이 남기려던 시간대를 개수 상한이 다시 깎아 조용히 구멍이 납니다.
- `min-backups`·`protect-manual`·`/wb lock` 은 안전장치라 계단과 무관하게 계속 동작합니다.
- 같은 구간에 전체 백업과 차등본이 함께 있으면 **전체 백업**을 대표로 남깁니다.
  차등본을 남기면 그 기준까지 함께 붙잡아야 해서 오래된 계단일수록 디스크가 두 배로 듭니다.
- 백업이 적어 첫 계단이 다 안 차면 전부 남습니다. 갓 설치한 서버에서 나이만 보고
  지워 버리는 일이 없도록 한 것입니다.

> **주기를 정하기 전에 멈춤 시간을 보세요.** 백업 한 번마다 청크 저장을 기다리느라 서버가
> 잠깐 멈춥니다. 콘솔의 `[백업] 청크 저장을 기다렸습니다 · world: 2.8초` 를 확인하고,
> 한 월드가 10초를 넘으면 주기를 더 줄이는 것은 무리입니다. 주기를 늘리고 첫 계단의 `keep` 만
> 줄이거나, 그 월드를 `targets.worlds` 에서 빼세요.
>
> 저장 전에 **쓰기를 미리 걸어 둡니다**(`backup.flush-settle-seconds`, 기본 3초). 멈추는
> 시간의 대부분은 청크를 만드는 비용이 아니라 이미 큐에 쌓인 쓰기가 디스크로 내려가기를
> 기다리는 것이라서, 기다리기 전에 큐를 비워 둡니다. 그 몇 초 동안 서버는 멈추지 않습니다 —
> 잠드는 것은 백업 스레드뿐입니다. (디스크가 빠르면 애초에 기다림이 없어 효과도 없습니다.
> NVMe 에서는 76ms → 74ms 로 차이가 없었습니다. `0` 으로 끌 수 있습니다.)
>
> 저장은 **월드마다 틱을 나눠** 돕니다. 워치독은 "틱 하나" 가 얼마나 걸렸는지를 보므로, 월드
> 셋을 한 틱에 몰아 저장하면 그 합이 한 틱의 길이가 됩니다 — 월드마다 4초씩만 걸려도 12초짜리
> 틱이 되어 `The server has not responded for 10 seconds` 와 스레드 덤프가 찍히고, 그 덤프에는
> 이 플러그인의 스택이 남습니다. 나눠도 멈추는 총량은 같지만 한 번에 멈추는 길이가 월드 수만큼
> 줄어듭니다.
>
> **참고할 실측값**: 26.2 실서버에서 갓 생성한 청크 4096개(region 파일 39개, 46 MB)를 한꺼번에
> 내려쓰게 만들어 재 봤더니, 저장 대기가 **1초에 닿지 않았고**(플러그인이 경고를 찍는 문턱)
> 백업 전체가 344ms 였습니다. 로컬 SSD·엔티티 없는 새 월드라 낙관적인 조건이지만, 멈춤이
> 문제가 되는 쪽은 주기보다 **디스크 속도와 로드된 청크 수**라는 것을 보여 줍니다.
> 회전식 디스크나 네트워크 스토리지에서는 이 값이 몇 배로 늘 수 있으니 꼭 직접 확인하세요.

> **테러는 CoreProtect 와 함께.** 전체 롤백은 테러범 것만 되돌리지 않습니다. 9시간을 되감으면
> 그동안 다른 사람이 정상적으로 한 것도 사라집니다. 건물 몇 개 부순 정도는 CoreProtect 로
> 그 사람 행동만 지우고, 인벤토리 털이나 대규모 파괴에 WorldBackUp 을 쓰는 편이 낫습니다.

### 보관 기간이 지나면 자동으로 지워지게 하려면

`retention.max-age-days` 가 그 옵션입니다. 다만 세 가지가 이 값보다 우선합니다.

- `keep-daily` — 최근 N일치는 하루 1개씩 무조건 남습니다. `max-age-days` 를 이보다 짧게 잡으려면 같이 줄이세요.
- `protect-manual` — 수동 백업과 복원 직전 백업은 나이와 무관하게 남습니다. (`max-protected` 개수 상한은 적용.
  단, `tiers`·`keep-daily` 가 그 시간대의 대표로 남기기로 한 백업은 상한으로 지우지 않습니다)
- `/wb lock` 으로 잠근 백업은 어떤 정책으로도 지워지지 않습니다.

"무조건 3일 지나면 삭제" 를 원한다면:

```yaml
retention:
  max-backups: 0
  max-age-days: 3
  keep-daily: 0
  protect-manual: false
```

정리는 **서버 시작 시, 백업 성공 후, 자동 백업을 건너뛴 주기마다** 자동으로 돌고, `/wb prune` 으로 즉시 실행할 수도 있습니다.

## OneBack — 서버 한 벌을 통째로

`/wb oneback` 을 치면 **서버 폴더에 있는 것을 통째로 담은 zip 하나**가 만들어집니다.

```
서버폴더/OneBack/
├── oneback-20260825-143000.zip   ← 서버 한 벌 전체
└── 읽어주세요.txt                 ← 다시 여는 방법
```

**이 폴더만 챙기면 아무 데서나 서버를 그대로 다시 열 수 있습니다.** 빈 폴더에 zip 을 풀고
서버 jar 를 실행하면 끝입니다. 절차는 `읽어주세요.txt` 에 적혀 있어서, 몇 달 뒤 그 폴더만
발견한 사람도(만든 사람이 아니어도) 복구할 수 있습니다.

| | 평소 백업 (`/wb backup`) | OneBack (`/wb oneback`) |
|---|---|---|
| 목적 | 이 서버를 **어제로 되돌리기** | 서버를 **아무 데서나 다시 열기** |
| 전제 | 서버 폴더가 있음 | 아무것도 없어도 됨 |
| 담는 것 | 월드 · 플레이어 데이터 · 설정 · `plugins/` | 그 전부 + **서버 jar** + `eula.txt` + `libraries/` |
| 크기 | 차등이면 수십 MB | 서버 폴더 크기만큼 |
| 주기 | 30분 (기본) | **수동** (기본) |
| 되돌리는 법 | `/wb restore` | 빈 폴더에 풀고 서버 실행 |

이럴 때 씁니다 — 호스팅을 옮길 때, 서버 폴더가 통째로 날아갔을 때(디스크 고장·계정 정지·실수),
큰 변경 전에 확실한 한 벌을 떠 둘 때.

> 기본값이 **수동**인 이유는 크기입니다. 한 번에 서버 폴더 크기만큼 씁니다. 자동으로 돌리시려면
> `oneback.interval-hours: 24`, `oneback.keep: 1~2` 를 권장합니다.
>
> `libraries/` 와 `versions/` 도 **일부러 담습니다** — 그게 있어야 인터넷 없는 환경에서도
> 그 자리에서 서버가 뜹니다. 로그·크래시 기록과 백업 폴더 자신은 빠집니다.
>
> 다른 디스크에 두면 더 안전합니다: `oneback.directory: "D:/oneback"`

## 7. 백업에 포함되는 것

- 월드 폴더 전체 (`region`, `entities`, `poi`, `data`, `level.dat`)
- **플레이어 데이터** — 인벤토리·좌표·경험치(`playerdata`), 통계(`stats`), 발전 과제(`advancements`)

  > 위치도 이름도 버전마다 다릅니다. 26.2 는 `world/players/data/<uuid>.dat` 에 두고, 그 전에는
  > `world/playerdata/` 였습니다. 플러그인이 **양쪽 이름과 위치를 모두 찾아** 자동으로 넣습니다.
  > (`players` 폴더를 찾으면 그 아래 `data/` 까지 통째로 담기므로 새 배치도 그대로 덮입니다.
  > 실서버 26.2 에서 플레이어 파일 하나를 심어 백업 → 인벤토리 초기화 → 복원까지 돌려
  > **바이트가 정확히 되돌아오고 서버가 그 파일을 문제없이 읽는 것**을 확인했습니다.)
  > 못 찾으면 서버 시작 시 콘솔에 경고가 뜨고, `/wb status` 에 <b>미포함</b>으로 표시되며,
  > 백업할 때마다 다시 경고합니다. 조용히 빠지지 않습니다.
  > (그때는 `targets.extra-paths` 에 실제 경로를 넣어 주세요.)
- `ops.json`, `whitelist.json`, `banned-players.json`, `usercache.json`, `server.properties` 등 서버 파일

  > 밴 목록(`banned-players.json`·`banned-ips.json`)은 **담기지만 복원 때 덮어쓰지 않습니다.**
  > 밴하고 되돌렸는데 밴이 풀리면 안 되기 때문입니다. 서버를 통째로 잃었을 때 쓸 수 있도록
  > 백업에는 계속 담기므로, 필요하면 zip 에서 직접 꺼내면 됩니다.
- **`plugins/` 폴더 전체** (`targets.plugins`, 기본 `all`)

  > 월드만 되돌리면 경제 잔고·보호구역·권한처럼 **플러그인이 들고 있는 상태**는 그대로 남아
  > 월드와 어긋납니다. 되돌린 시점에는 없던 상점 거래가 그대로 살아 있고, 사라진 건물의
  > 보호구역이 그대로 남는 식입니다.
  >
  > **jar 는 담기지만 복원 때 덮어쓰지 않습니다.** 복원은 월드가 올라오기 전(`onLoad`)에
  > 도는데, 그 시점에는 서버가 이미 모든 플러그인 jar 를 열어 둔 뒤입니다. 윈도우에서는
  > 파일이 잠겨 실패하고, 리눅스에서는 성공해도 이번 세션에는 아무 효과가 없이 **다음
  > 재시작에 조용히 옛 버전으로 돌아갑니다.** 게다가 사흘 전으로 되돌릴 때 원하는 것은 대개
  > "지금 코드 + 그때 데이터" 이지 사흘 전 버전의 플러그인이 아닙니다. 서버를 통째로 잃었을
  > 때 쓸 수 있도록 담기기는 하므로, 필요하면 zip 에서 직접 꺼내면 됩니다.
  >
  > `data` 로 두면 jar 를 아예 담지 않습니다(`plugins/` **바로 아래**만 — 플러그인이 자기
  > 폴더 안에 두는 라이브러리 jar 는 그 플러그인의 데이터라 함께 담습니다).
  >
  > 데이터베이스를 열어 둔 채 쓰는 플러그인(SQLite/H2 등)은 백업 순간의 파일이 잘려 있을 수
  > 있습니다. 그런 폴더는 `targets.exclude` 에 넣으세요.
  >
  > 복원은 이 폴더도 "백업 시점 그대로" 만듭니다. 백업한 뒤에 설치한 플러그인의 **데이터
  > 폴더는 사라집니다**(jar 는 위 규칙으로 남습니다). `restore.keep-replaced-files` 가 켜져
  > 있으면 `plugins/WorldBackUp/replaced/` 로 옮겨 두므로 되찾을 수 있습니다.
- `targets.extra-paths` 에 지정한 추가 경로
- **이 플러그인의 `config.yml`** — 담지 않으면 서버를 되돌려도 그 시점의 보관 정책은
  되돌아오지 않습니다. 백업이 어떻게 만들어졌는지가 정작 백업 안에 없는 셈입니다.

  > 복원하면 이 파일도 그 시점 것으로 바뀝니다. 그 뒤 `backup.directory` 같은 값이 예전으로
  > 돌아갈 수 있으니 복원 후 `/wb status` 로 한 번 확인하세요. 원치 않으면 `targets.exclude` 에
  > `"plugins/WorldBackUp/config.yml"` 을 넣으면 됩니다.
  >
  > 반대로 플러그인이 **스스로 만들어 쓰는 것**(`backups/`, `replaced/`, 복원 예약 파일,
  > 실패 표식)은 절대 담기지 않습니다. 담기면 복원이 그것을 되살리는데, 복원 예약이 되살아나면
  > 다음 부팅이 **또 복원을 시작하고**, 실패 표식이 되살아나면 아무도 손대지 않은 서버에서
  > 자동 백업이 영구히 멈춥니다.

> `extra-paths` 에 이미 백업되는 월드의 하위 경로(`world/playerdata` 등)를 적어도 괜찮습니다.
> 겹치는 대상은 상위 경로 하나로 합쳐지고, 어떤 항목이 합쳐졌는지 콘솔에 남습니다.

## 8. 동작 방식 / 주의사항

**백업**
1. 메인 스레드에서 `savePlayers()` → 각 월드 `save(true)` → 자동 저장 OFF

   > `save(true)` 는 **청크 쓰기가 디스크에 끝날 때까지 기다립니다.** 그동안 서버가 잠깐
   > 멈추고(월드 크기에 따라 수 초), 1초를 넘으면 콘솔에 대기 시간이 남습니다.
   > 기다리지 않으면 서버가 아직 쓰고 있는 region 파일을 압축하게 되어, 헤더와 데이터가
   > 어긋난 조각이 백업에 담깁니다. 그런 백업으로 복원하면 `Corrupt regionfile header` 가
   > 뜨고 복구되지 않은 청크는 재생성됩니다. 멈춤을 감수할 값어치가 있습니다.
2. 비동기 스레드에서 `wb-<ID>.zip.tmp` 로 압축 (진행률을 5초마다 콘솔 출력)

   > **이미 압축된 파일은 다시 압축하지 않습니다.** 마인크래프트는 청크를 zlib 으로 눌러
   > region 파일(`.mca`)에 담으므로, 월드 용량의 대부분이 이미 압축된 바이트입니다.
   > 거기에 deflate 를 한 번 더 걸면 **크기는 그대로인데 CPU 만 몇 배로** 먹습니다.
   > 측정해 보면 region 부분만 레벨 0 대비 14배(47ms → 658ms) 느려지면서 절감은 0.0% 였고,
   > 반대로 텍스트·JSON·YAML 은 98.7% 가 줄면서 비용은 거의 없었습니다.
   > 그래서 `.mca`/`.mcc`/`.mcr`·`.gz`/`.zip`/`.jar`·`.png`/`.ogg` 같은 형식은 무압축으로 담고
   > 나머지에만 `compression-level` 을 적용합니다. **결과물 크기는 사실상 그대로이고
   > 백업 시간은 8배 짧아집니다**(31MB 월드: 753ms → 94ms). 얼마를 건너뛰었는지는
   > 콘솔의 `[백업] 이미 압축된 파일 … 는 재압축하지 않았습니다` 로 확인할 수 있습니다.
3. 압축이 정상적으로 끝나야 `wb-<ID>.zip` 으로 이름을 바꿉니다
4. 메인 스레드에서 자동 저장 원복 → 보관 정책에 따라 오래된 백업 정리

   > **차등 백업은 대상을 두 번 훑지 않습니다.** 압축 전에 용량을 재는 순회가 하나 더 있는데,
   > 그것이 필요한 이유는 둘 뿐입니다 — 디스크 여유 판정과 진행률 분모. 기준 백업의
   > 스냅샷 크기(`original-bytes`)를 넉넉히 잡아도 여유가 남는다면 두 답을 이미 아는 것이므로
   > 그 순회를 통째로 건너뜁니다. 파일마다 `stat` 을 하는 순회라 캐시가 식어 있으면 비싸고,
   > 파일 2만 개 월드에서 차등 백업 한 주기가 **114ms → 79ms** 로 줄었습니다.
   > 여유가 빠듯하거나 기준에 크기 기록이 없으면 예전처럼 정확히 재고, 필요하면 공간을 만듭니다.

자동 저장 원복은 백업이 어떤 이유로 실패하든(타임아웃 포함) 반드시 실행되고,
서버 종료 시점에도 한 번 더 확인합니다. 자동 저장이 꺼진 채 방치되면 크래시 시
그 세션 전체가 날아가기 때문입니다.

**복원**
- 서버 실행 중에는 region 파일이 열려 있어 교체가 불가능하므로,
  `pending-restore.yml` 예약 파일을 남기고 서버를 종료합니다.
  예약 파일은 **실제로 종료하기 직전에** 기록되므로, 카운트다운 도중 서버를 강제로 꺼도
  의도치 않은 복원이 일어나지 않습니다.
- 다음 부팅 시 플러그인 `onLoad()`(월드 로드 직전)에서
  ① zip 무결성 검사 → ② 대상 폴더 비우기 → ③ 압축 해제 순으로 진행합니다.
  ①에서 실패하면 **기존 월드를 전혀 건드리지 않고** 중단합니다.

  > ①이 아카이브를 한 번 다 읽으므로 복원은 아카이브를 **두 번** 읽습니다. 이것은 낭비가
  > 아니라 그 안전 보장 자체입니다 — 읽어 보지 않고는 zip 이 멀쩡한지 알 수 없고, 이미
  > 월드를 지운 뒤에 알게 되면 되돌릴 것이 없습니다. 재 보면 검사는 I/O 바운드로 돌아가고
  > (압축 여부와 무관하게 같은 속도) 복원 전체 시간을 대략 절반쯤 늘립니다. 평생 한 번
  > 할지도 모르는 작업에 그 값을 치를 이유는 충분하지만, 원치 않으시면
  > `restore.verify-archive: false` 로 끌 수 있습니다.
  >
  > 한 번만 읽게 만들려면 "임시 폴더에 풀고 마지막에 갈아 끼우기" 로 바꿔야 하는데,
  > 월드 크기만큼의 여유 공간을 **항상** 요구하게 되고 가장 위험한 코드 경로를 다시 쓰는
  > 일입니다. 드문 작업의 2배를 얻으려고 치를 값이 아니라고 보고 두었습니다.
- **공간도 지우기 전에 확인합니다.** 복원은 "비우고 푸는" 순서라 푸는 도중에 디스크가 차면
  반쯤 복원된 월드만 남습니다. 필요한 양은 백업의 파일 목록에서 정확히 계산하고, 모자라면
  월드를 건드리기 전에 멈춥니다. 그 전에 오래된 `replaced/` 스냅샷을 `keep-replaced-max`
  기준으로 정리해 자리를 만들어 봅니다 — 플러그인 자기 잔재가 정작 되돌려야 할 때 길을 막으면
  안 되기 때문입니다. `/wb restore` 확인 화면에도 필요/남은 공간이 표시되어, **확정하기 전에**
  알 수 있습니다.
  (`keep-replaced-files: false` 면 지우면서 공간이 돌아오므로 막지 않고 경고만 합니다.)
- 백업에 내용이 없는 경로(백업 시점에 비어 있던 `extra-paths` 폴더 등)는 **비우지 않고 건너뜁니다.**
  비우기만 하고 채우지 않으면 그 폴더가 사라지기 때문입니다. 콘솔에 어떤 경로를 건너뛰었는지 남고,
  모든 대상에 내용이 없을 때만 복원을 거부합니다.
- 복원이 중간에 끊기면 `restore-failed-<시각>.yml` 이 생기고 **재시도 루프에 빠지지 않습니다**.
  이 경우 서버를 끄고 `replaced/` 폴더를 이용해 수동 확인이 필요합니다.
- **op·화이트리스트는 파일을 되돌리는 것만으로는 적용되지 않습니다.** 서버가 이 파일들을
  플러그인보다 **먼저** 읽어 메모리에 올려 두기 때문입니다. 그래서 월드가 올라온 직후
  (`onEnable`) 서버가 들고 있는 목록을 백업 시점으로 **맞춰 넣습니다.** 누가 op 가 되고 누가
  내려갔는지는 콘솔에 이름으로 남습니다.

  > 이 단계가 없으면 복원은 "성공" 이라고 말하면서 op 를 하나도 바꾸지 않습니다. 그리고 다음
  > `/op` 한 번에 서버가 메모리를 파일로 덮어써서, 되돌려 놓은 `ops.json` 마저 사라집니다.
  > 하필 op 를 잃은 관리자가 가장 먼저 하게 되는 명령입니다.
  >
  > 목록 파일을 읽지 못하면 **아무것도 건드리지 않고** 크게 알립니다 — "읽지 못했다" 를
  > "아무도 없었다" 로 받아들이면 전원이 op 에서 내려가고, 그러면 게임 안에서 되돌릴 방법이
  > 없습니다. 반대로 백업 시점에 정말로 op 가 없었다면 전원이 내려갑니다(그게 그 백업의
  > 내용입니다). 그때는 콘솔에서 `op <이름>` 으로 올려 주세요.
- **밴 목록은 되돌리지 않습니다.** `banned-players.json` 과 `banned-ips.json` 은 복원이 아예
  덮어쓰지 않으므로, **밴한 사람은 되돌린 뒤에도 그대로 밴입니다.**

  > 이 플러그인을 쓰는 가장 흔한 순간이 "테러범을 밴하고 그 전으로 되돌리는" 것입니다.
  > 밴까지 되돌리면 방금 건 밴이 함께 풀려 같은 사람이 곧바로 다시 들어옵니다 — 복원이 사고를
  > 반쯤 되살리는 셈입니다. 백업에는 계속 담기므로, 서버를 통째로 잃었을 때는 zip 에서 직접
  > 꺼내 쓸 수 있습니다.

**알아 두면 좋은 점**
- 백업 중 자동 저장을 꺼도 청크 언로드, 플레이어 퇴장 시 `playerdata` 기록, 다른 플러그인의
  파일 쓰기는 계속됩니다. 즉 **완벽한 스냅샷은 아닙니다.** region 파일은 청크 단위 구조라
  피해가 국소적이지만, 완전한 정합성이 필요하면 파일 시스템 스냅샷(LVM/ZFS/VSS)을 쓰세요.
- 압축 도중 서버가 죽으면 `.zip.tmp` 만 남고, 다음 시작 시 자동으로 정리됩니다.
  혹시 손상된 백업이 목록에 보이면 `/wb list` 에 <b>[손상]</b> 으로 표시되고 복원에 사용할 수 없습니다.
- 메인 월드의 `level.dat`(시간·날씨·게임룰 등)과 `server.properties`·`bukkit.yml`·`spigot.yml` 은
  서버가 부팅 초기에 이미 메모리로 읽어 두기 때문에, 복원 직후 한 세션 동안은 이전 값이 유지됩니다.
  **어떤 파일이 그런 상태인지는 복원 직후 콘솔에 이름으로 남고**, 서버를 한 번 더 껐다 켜면
  적용됩니다. 지형·건축물·플레이어 데이터는 영향받지 않으며, op·화이트리스트는 위에 적은 대로
  그 자리에서 맞춰 넣으므로 재시작이 필요 없습니다. (밴은 애초에 되돌리지 않습니다)
- 백업 중 잠긴 파일(`session.lock` 등)은 건너뛰며, 건너뛴 개수는 콘솔에 표시됩니다.
  **건너뛴 파일은 "담긴 것" 으로 기록되지 않습니다.** 아카이브 안에 무엇이 들었는지는 zip 의
  엔트리 목록이 아니라 함께 저장되는 파일 목록(`worldbackup-files.txt`)이 정하고, 거기에는
  끝까지 담아낸 파일만 적힙니다. 그래서
  ① 복원이 멀쩡한 파일을 빈/잘린 파일로 덮어쓰지 않고,
  ② 다음 차등 백업이 "기준에 이미 있다" 고 착각해 그 파일을 빠뜨리지 않습니다.
  차등 복원이라면 기준 백업에 있는 예전 판으로 되돌리고, 그럴 수 없으면 그 파일만 남겨 둡니다.
  어느 쪽이든 복원 시 콘솔에 파일 이름이 남습니다.
- 백업 폴더가 서버 폴더 안에 있으면 자기 자신을 백업하지 않도록 자동으로 제외합니다.
- 백업본은 **다른 물리 디스크**에 두는 것을 권장합니다 (`backup.directory` 에 절대 경로 지정).
- 블록 단위로 "누가 무엇을 부쉈는지" 되돌리려면 CoreProtect 같은 로그 기반 플러그인을 함께 쓰세요.
  이 플러그인은 서버 전체를 특정 시점으로 되돌리는 용도입니다.

## 9. 서버 호환성

| 항목 | 상태 |
|---|---|
| Paper 26.2 | 지원 |
| 명령어 | Brigadier 로 등록합니다. 인자 타입과 권한이 인자 단위로 검증됩니다 |
| 스케줄러 | `AsyncScheduler` / `GlobalRegionScheduler` (현대 Paper API) |
| Folia | **미지원.** 로드되지 않습니다 |

스케줄링은 [`util/Sched.java`](src/main/java/io/github/yj/worldbackup/util/Sched.java) 한 곳에 모아
두어 Folia 이관 시 손볼 범위를 좁혔습니다. 다만 Folia 는 월드 저장이 리전별로 쪼개져 있어
이 플러그인의 전제인 "전 월드를 동시에 얼린 스냅샷"이 성립하지 않습니다. 스케줄러만 바꿔서는
안 되고 백업 로직 자체를 다시 설계해야 하므로, 검증 없이 `folia-supported` 를 선언하지 않았습니다.

플러그인 로딩은 `plugin.yml` 방식을 유지합니다. `paper-plugin.yml` 로 옮기면 로딩·클래스로딩
모델이 바뀌는데, 이 플러그인의 핵심 보장인 "복원은 월드 로드 전에 실행된다"가 여기에 달려 있어
실서버 검증 없이는 건드리지 않았습니다.

## 10. 테스트

```bash
./gradlew test
```

푸시와 PR 마다 [GitHub Actions](.github/workflows/build.yml) 가 JDK 25 에서 같은 명령을 돌립니다.
테스트가 백여 개 있어도 자동으로 돌지 않으면 "돌렸다고 믿는 것"에 그치고, 여기서 검증하는 것들은
대부분 잘못되면 **조용히** 데이터를 잃는 분기라 회귀를 사람 손에 맡기지 않았습니다.

- `BackupRestoreRoundTripTest` — 백업 → 지형 삭제/인벤토리 초기화/파일 추가(테러 재현) → 복원 → 원상복구 검증,
  중단된 복원의 무한 루프 방지, zip slip 방어, 차등 백업의 스냅샷 정확성(삭제된 파일·빈 폴더가 되살아나지 않는지),
  보존 대상 폴더는 비어 있어도 복원이 지우지 않는지
- `ArchiverUnreadableFileTest` — 서버가 쓰고 있어 <b>읽지 못한</b> 파일이 "담긴 것" 으로 기록되지 않는지.
  이것이 어긋나면 복원이 멀쩡한 파일을 빈 파일로 덮어쓰고, 다음 차등본은 그 파일을 아예 담지 않습니다.
  "열기가 실패" 하는 상황과 "첫 조각을 읽은 뒤 끊기는" 상황을 모두 재현합니다.

  > 읽기 실패는 **주입**합니다. 예전에는 `FileLock` 으로 흉내 냈는데, 그 잠금은 **윈도우에서만
  > 강제**라 리눅스에서는 읽기가 그냥 성공하고 검증이 조용히 통과했습니다. 정작 이 플러그인이
  > 대부분 돌아가는 플랫폼에서 가장 중요한 보장이 확인되지 않았던 것입니다 (CI 를 붙이자마자
  > 이 이유로 다섯 개가 깨졌습니다). 실제 OS 잠금이 정말 같은 모양인지는 그것이 가능한
  > 플랫폼에서 한 테스트가 따로 확인합니다.
- `BackupServiceTest` — 백업의 **실패·정지 경로**. 복원 실패 정지 중에는 보관 정리도 공간 확보도 하지 않는지,
  압축이 끝난 백업을 뒷정리 실패로 지우지 않는지, 어떤 경로로 실패해도 자동 저장이 원복되는지.
  용량 측정 순회를 건너뛰는 판단이 경계에서 보수적인지, 건너뛰어도 담는 파일이 같은지,
  여유가 빠듯하면 예전처럼 거부하는지
- `BackupRetentionTest` — 보관 정책. 나이/개수 상한, `keep-daily`, 수동 백업 보호와 `max-protected` 상한,
  `/wb lock` 의 절대 보호, 차등본이 살아 있는 기준 백업 보존, 총 용량 상한, 공간 확보의 최소 개수 하한,
  남은 임시 파일 정리, 목록 캐시가 스캔 중의 변경을 되살리지 않는지(스레드를 붙잡아 재현)
- `RetentionTiersTest` — 계단식 보관의 구간 나누기. 대표 선정(전체 백업 우선·손상 제외), 미래 시각 백업, 이력의 공백
- `RestoreDecisionTest` — 복원을 **확정하기 전에** 내리는 판단. `worlds` 가 월드만 고르는지
  (새면 `server.properties` 까지 되돌아갑니다), 월드를 못 찾으면 전체로 넓히지 않고 빈 목록을 주는지,
  백업에서 제외했던 것이 복원에서도 보존되는지, 공간 점검이 경계와 "기록 없는 옛 백업" 에서 관대한지
- `CommandHelpCoverageTest` — 등록한 명령이 전부 `/wb help` 에 있는지. 빠져도 아무 데서도
  티가 나지 않고(명령은 정상으로 돌고 탭 완성에도 뜹니다) **아무도 그런 명령이 있는 줄 모를**
  뿐이라, 사람 눈에 기대지 않습니다. 실제로 `/wb oneback` 을 붙일 때 빠뜨렸습니다
- `OneBackTest` — **아카이브 하나로 서버를 다시 열 수 있는가.** 실제로 아카이브를 만들어
  안에 무엇이 들었는지 확인합니다 — 서버 jar, `eula.txt`, 월드, 인벤토리, 다른 플러그인의
  jar 와 데이터까지. 이 약속은 **무엇이 빠졌는지**로만 깨지고, 그 사실은 정작 서버가 날아간
  뒤에야 드러납니다. 자기 자신과 평소 백업을 삼키지 않는지, 복원 예약 같은 제어 파일이
  되살아나지 않는지도 함께 봅니다
- `PluginJarsTest` — 플러그인 jar 는 **담기되 되돌려지지 않는다**는 경계. 다른 플러그인
  (`mopi`, `EventSystem` 등)의 jar 와 데이터가 실제 경로 기준으로 백업에 들어가는지까지 확인합니다
- `UpgradeFromOneZeroSimulationTest` — **jar 만 갈아 끼웠을 때 서버에서 실제로 무슨 일이 일어나는지.**
  1.0.0 서버 폴더를 통째로 만들어 놓고(1.0.0 설정 원본·백업 48개·월드) 플러그인이 올라오는
  순서 그대로 실제 코드를 태웁니다 — 설정 이행 → 재로드 → 보관 정리 → 복원. 업데이트가
  **되돌릴 수 있는 시점을 하나도 줄이지 않는지**를 숫자로 못 박습니다. 잠근 백업이 남는지,
  차등본이 기준을 잃지 않는지, 꺼진 채로 들어온 기능을 관리자가 켤 수 있는지까지 확인합니다
- `LegacyBackupCompatTest` — 1.0.0 이 만든 백업을 지금 코드가 되돌릴 수 있는지. 아카이브를
  1.0.0 형식(파일 목록에 "담지 못함" 표시 없음, 메타에 `player-data` 없음)으로 직접 만들어
  복원합니다. 여기가 깨지면 업그레이드한 순간 **되돌릴 시점이 하나도 없는 서버**가 되는데,
  그 사실은 정작 되돌려야 하는 날에야 드러납니다
- `ConfigMigratorTest` — 관리자의 `config.yml` 을 다시 쓰는 코드. 쓴 줄이 하나도 사라지지
  않는지, 새 설정이 제 묶음 안에 들어가는지, 그리고 **동작을 바꿀 수 있는 새 기본값이 꺼진
  채로 들어오는지**
- `UserListsTest` — 복원이 되돌린 **op·화이트리스트 파일**을 읽고 무엇을 넣고 뺄지 정하는 판단.
  특히 "파일을 **읽지 못한 것**" 과 "정말로 **비어 있는 것**" 을 갈라 놓습니다 — 같이 취급하면
  JSON 한 글자 때문에 전원이 op 에서 내려가고, 그러면 관리자가 게임 안에서 되돌릴 수단이 없습니다.
  밴 목록이 이 대상에 **들어가지 않는지**도 함께 못 박습니다(밴은 되돌리지 않습니다)
- `OwnDataFolderExclusionTest` — 플러그인 자기 폴더에서 무엇을 담고 무엇을 빼는지. 이 경계는
  **양쪽으로** 위험하다 — 넓으면 `config.yml` 이 빠져 보관 정책을 복원할 수 없고, 좁으면 복원 예약이나
  실패 표식이 담겼다가 복원으로 되살아난다. 저장 위치를 옮긴 뒤에도 옛 아카이브가 계속 제외되는지까지 확인
- `PlayerDataTest` — 인벤토리 폴더 탐색. `players`/`playerdata` 양쪽 배치, 플러그인 폴더 오탐 방지
- `WorldLayoutTest` — 차원 폴더에서 진짜 월드 폴더로 올라가기
- `SuggestionHintTest` — 탭 완성 설명이 명령이 실제로 고르는 백업과 일치하는지.
  두 계산이 갈라지면 사고 직후에 설명을 믿고 엉뚱한 시점으로 되돌아가게 됩니다
- `CommandGuardsTest` — **파괴적인 명령이 무엇을 거부하는지.** `/wb delete`·`/wb lock`·`/wb prune`
  의 판단을 [`CommandGuards`](src/main/java/io/github/yj/worldbackup/command/CommandGuards.java) 로
  떼어 내 서버 없이 검증합니다. 특히 "잠긴 차등본이 딸린 기준 백업은 `cascade` 를 붙여도 거부"
  처럼 **검사 순서가 곧 계약**인 것들을 못 박습니다 — 순서가 밀리면 `/wb lock` 으로 잠근 백업이
  명령 한 번에 사라집니다. 판단부가 다시 Bukkit 에 묶이지 않는지도 테스트가 지켜봅니다
- `GlobMatcherTest` — 제외/보존 패턴 매칭 (윈도우 `\` 경로 포함). `**/X` 를 마지막 경로 조각만
  검사하도록 최적화했으므로, 그 지름길이 답을 바꾸지 않는지(특히 `**` 가 꼬리에 들어간 경우)까지 확인
- `SymlinkTargetTest` — 심볼릭 링크로 옮긴 월드도 백업되고, 복원이 링크 자체를 치우지 않는지.
  링크를 따라가지 않으면 그 아래가 통째로 빠지는데 **백업은 성공한 것처럼 끝납니다.**
  (윈도우에서는 링크 생성 권한이 없어 건너뜁니다 — 리눅스 CI 가 검증합니다)
- `FileUtilTest` — 겹치는 백업 대상 병합, 상대 경로 변환, 차등 백업의 변경분 용량 측정
- `TimeTokenTest` — `9h`·`03:00`·절대 시각 해석

> 서버 인스턴스가 필요한 부분은 [`ServerBridge`](src/main/java/io/github/yj/worldbackup/backup/ServerBridge.java)
> 하나로 모아 두었습니다. `BackupService` 는 이 인터페이스만 보고 돌기 때문에, 지우고 되돌리는 판단을
> Paper 없이 검증할 수 있습니다. 실서버 구현은
> [`PaperServerBridge`](src/main/java/io/github/yj/worldbackup/PaperServerBridge.java) 한 곳뿐입니다.
>
> 서버 없이는 돌릴 수 없는 흐름(명령어 트리, 복원 확정 → 카운트다운 → 종료)에서도 **판단만은**
> 순수 함수로 떼어 내 테스트합니다. `hasAmpleRoom`·`hasRoomToRestore`·`selectedRoots` 처럼
> `public static` 인 것들이 그것이고, 각 메서드의 주석에 "왜 public 인가" 가 적혀 있습니다.
